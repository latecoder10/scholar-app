## 1.1 — Agentic loops, `stop_reason`, and loop termination

**Governing principle for this section.** The API tells you when the turn is over, and `stop_reason` is that contract. `"tool_use"` means *execute the tools, append the results, call again*; `"end_turn"` means *the model is finished*. Termination logic built on response **text** ("Done", "Task complete", `content[0].type == "text"`) or on an **iteration counter as the primary signal** is an anti-pattern. Iteration caps are legitimate only as a safety backstop layered on top of `stop_reason` — never as a replacement for it.

### UD1-005

**Q.** Your agentic loop checks if `response.content[0].type` equals `"text"` to determine completion. The agent sometimes terminates prematurely mid-task; production logs show tasks incomplete when the agent could continue. What causes premature termination?

- A. Checking for text content instead of stop_reason creates false termination signal.
- B. Agent lacks sufficient tools to complete tasks requiring premature termination.
- C. Context window exhaustion prevents agent from continuing with additional iterations.
- D. Max iteration count reached before task completion causing early stop.

**✅ Answer: A**

**Why it's correct.** A single assistant turn can contain *mixed* content blocks — Claude routinely emits a `text` block ("I'll look up that order first…") followed by one or more `tool_use` blocks in the same message. Because `content[0]` is the *first* block, a leading narration block makes the check fire even though the turn's `stop_reason` is `"tool_use"` and work remains. A block's type describes *what a piece of the message is*, not *whether the turn is complete*; only `stop_reason` carries that meaning.

**Why the others fail.**
- **B** — Missing tools produce a different signature: the model says it cannot proceed, or hallucinates a tool. That does not make a content-type check fire early.
- **C** — Context exhaustion surfaces as `stop_reason: "max_tokens"` or an API error, not as a silent early exit through this code path.
- **D** — The stem states the loop terminates on a content-type check; no iteration cap is described, and a cap would truncate at a fixed count rather than "sometimes, mid-task."

**Source.** [Handling stop reasons](https://docs.claude.com/en/api/handling-stop-reasons) · [Tool use overview](https://docs.claude.com/en/docs/agents-and-tools/tool-use/overview)

### UD1-009

**Q.** An agent repeatedly calls the same tool with identical parameters after receiving successful responses, creating an infinite loop. What is the most appropriate architectural safeguard?

- A. Increase the maximum iteration limit so the agent has more opportunities to finish.
- B. Add explicit loop detection by tracking repeated tool invocations and terminate or escalate when repetition is detected.
- C. Improve the system prompt instructing the agent not to repeat tool calls.
- D. Add more tools so the agent has additional choices.

**✅ Answer: B**

**Why it's correct.** The failure is *spinning*: repeated action with no new information. The harness — not the model — is the reliable place to detect it, because the harness holds a deterministic record of every `(tool_name, input)` pair it has executed. Hashing invocations and tripping on repeats gives a hard guarantee, and it gives you an **escalation path** (surface to a human, inject a corrective observation, or terminate with a partial result) instead of a silent hang.

**Why the others fail.**
- **A** — Raising the limit makes an unbounded loop *more* expensive, not bounded. The loop never converges; extra headroom just burns tokens.
- **C** — Prompt instructions are probabilistic guidance. They reduce frequency at best; they cannot guarantee termination, and this is a reliability requirement.
- **D** — More tools widen the action space and typically worsen selection confusion. It does nothing about repetition of one call.

**Source.** [Building effective agents — guardrails and stopping conditions](https://www.anthropic.com/engineering/building-effective-agents) · [Claude Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)

### UD1-012

**Q.** The loop continues while `stop_reason == "tool_use"` and terminates on `"end_turn"`. The agent sometimes continues after completing the task; logs show `end_turn` received but the loop continues. What causes continued iteration after completion?

- A. Context window size affects stop_reason reliability in long conversations.
- B. Tool results appended to conversation causing unexpected tool_use stop_reason.
- C. Multiple stop_reason values can occur requiring checking all values.
- D. Checking additional conditions beyond stop_reason creates continuation logic errors; `stop_reason="end_turn"` is definitive completion.

**✅ Answer: D**

**Why it's correct.** `stop_reason` is a **single scalar** on each response, and `"end_turn"` is authoritative: the model finished its turn of its own accord. If the loop still iterates after receiving it, the only remaining explanation is that some *additional* condition in the loop predicate (a text check, a "did we get a final answer?" heuristic, a leftover flag) is overriding the definitive signal. The fix is to make `stop_reason` the sole continuation predicate.

**Why the others fail.**
- **A** — `stop_reason` is not degraded by conversation length; a near-full window produces `max_tokens` or an error, not an unreliable `end_turn`.
- **B** — Appending tool results is required behaviour and cannot retroactively change a `stop_reason` you have already received.
- **C** — A response carries exactly one `stop_reason`. There is no set of simultaneous values to check.

**Source.** [Handling stop reasons](https://docs.claude.com/en/api/handling-stop-reasons) · [Messages API reference](https://docs.claude.com/en/api/messages)

### UD1-029

**Q.** A production loop terminates when the response contains text content, assuming completion. The agent sometimes provides an explanation then continues with tool_use, so the loop terminates before tool execution. What is the correct loop termination signal?

- A. Presence of text content in response indicates agent has completed reasoning and task.
- B. Maximum iteration count threshold as primary termination mechanism for safety.
- C. Check `stop_reason` value for `end_turn` as authoritative completion signal, not text content.
- D. Count tool_use occurrences in response; zero tool calls indicates completion.

**✅ Answer: C**

**Why it's correct.** Same root cause as UD1-005, stated from the opposite direction. Text and tool-use blocks coexist inside one turn; the API's explicit completion contract is `stop_reason == "end_turn"`. Reading it is O(1), unambiguous, and stable across model versions.

**Why the others fail.**
- **A** — This *is* the bug described in the stem.
- **B** — An iteration cap is a backstop, not a completion signal; used as the primary mechanism it truncates unfinished work and lets finished work spin to the ceiling.
- **D** — Counting `tool_use` blocks is a *derived proxy*. It coincides with `end_turn` in the common case but silently mishandles turns that stop for other reasons — `max_tokens`, `pause_turn`, `refusal` — which also contain zero tool calls yet are not successful completions. Read the field; don't infer it.

**Source.** [Handling stop reasons](https://docs.claude.com/en/api/handling-stop-reasons) · [Implement tool use](https://docs.claude.com/en/docs/agents-and-tools/tool-use/implement-tool-use)

### UD1-049

**Q.** The loop continues while `stop_reason == tool_use` and stops on `end_turn`. It *also* checks whether the response contains "DONE" text, triggering termination. What causes incorrect early loop termination?

- A. Text-based completion detection in addition to stop_reason creates false termination triggers.
- B. Text checking necessary as backup when stop_reason values are unreliable.
- C. Both stop_reason and text conditions required for robust production termination.
- D. Multiple termination conditions improve robustness catching all possible completion signals.

**✅ Answer: A**

**Why it's correct.** The added text check is a second, weaker trigger **OR-ed** into the termination predicate. "DONE" can legitimately appear inside reasoning ("the migration is not DONE until…"), inside quoted log output, or as a code identifier — so the loop exits on a coincidence. Adding conditions to an OR broadens termination; it does not harden it.

**Why the others fail.**
- **B** — `stop_reason` is a documented, guaranteed field. "Unreliable" is a false premise.
- **C** — Requiring *both* would be an AND, which the stem does not describe — and it would then hang whenever the model finishes without saying "DONE".
- **D** — Inverts the reliability logic: more OR-ed triggers means more false positives, not more robustness.

**Source.** [Handling stop reasons](https://docs.claude.com/en/api/handling-stop-reasons) · [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

### UD1-052

**Q.** A developer's Agent SDK agent definition includes 3 tools and a system prompt. When they call `agent.run()`, what happens internally?

- A. The SDK sends the tools to a separate tool execution service and polls for results.
- B. The SDK makes a single API call with all tools and returns the complete result.
- C. The SDK enters an agentic loop: sends messages to Claude, receives a response, checks for `tool_use` blocks, executes any tools, appends tool results to the conversation, and continues until Claude responds with `end_turn`.
- D. The SDK makes parallel API calls.

**✅ Answer: C**

**Why it's correct.** This is the canonical agentic loop, and automating it is exactly what the SDK harness is for: request → inspect `stop_reason` → execute the requested tools → append `tool_result` blocks as a user message → request again → repeat until `end_turn`. The SDK's value is owning that loop (plus context management, permissions, and hooks) so you only write tool bodies.

**Why the others fail.**
- **A** — Tool execution is local to your process (client-side tools). There is no separate execution service to poll. The only server-executed tools are Anthropic's server tools (web search, web fetch, code execution), a different mechanism entirely.
- **B** — One call cannot complete a tool-using task: the first response *requests* tools, it does not contain their results.
- **D** — Parallelism exists *within* a turn (several `tool_use` blocks executed concurrently), not as parallel API calls replacing the loop.

**Source.** [Claude Agent SDK — overview](https://code.claude.com/docs/en/agent-sdk/overview) · [Implement tool use — the agentic loop](https://docs.claude.com/en/docs/agents-and-tools/tool-use/implement-tool-use)

### UD1-055

**Q.** Streaming a response containing both text and thinking blocks; thinking must render in a separate UI panel. How do streaming events distinguish thinking from text content?

- A. Thinking content uses a different streaming endpoint from text content.
- B. Thinking content arrives first, followed by text content.
- C. All content arrives in the same stream with inline markdown tags to distinguish thinking.
- D. Streaming events include a `content_block_start` event with the block type (`thinking` or `text`), allowing the client to route content to the appropriate UI panel.

**✅ Answer: D**

**Why it's correct.** The streaming protocol is block-structured. Each content block opens with a `content_block_start` event carrying an `index` and a typed `content_block` (`{"type": "thinking"}` or `{"type": "text"}`), then emits `content_block_delta` events (`thinking_delta` / `text_delta`) against that index, then `content_block_stop`. Routing is therefore a switch on a declared type — no parsing, no heuristics.

**Why the others fail.**
- **A** — There is one streaming endpoint: `/v1/messages` with `stream: true`.
- **B** — Ordering is a convention, not a guarantee you can build UI routing on; with interleaved thinking, thinking and text can alternate across a turn.
- **C** — Thinking is never delivered as inline markdown tags inside text. (Leaked `<thinking>` tags are a known symptom of *disabling* thinking on current models — a bug, not the protocol.)

**Source.** [Streaming messages — event types](https://docs.claude.com/en/docs/build-with-claude/streaming) · [Extended thinking](https://docs.claude.com/en/docs/build-with-claude/extended-thinking)

### UD1-057

**Q.** Three subagents (researcher, analyzer, reporter). The researcher frequently gets stuck in recursive web searches, making dozens of tool calls without converging. What architectural pattern prevents this?

- A. Add a PostToolUse hook that counts tool calls and terminates after 10.
- B. Increase the researcher's context window to give it more room for exploration.
- C. Remove the researcher subagent and have the main agent do research directly.
- D. Set an iteration limit for the researcher subagent and require it to report findings at the limit even if incomplete.

**✅ Answer: D**

**Why it's correct.** Two things are needed and D supplies both: a **bound** on the subagent's exploration, and a **defined output contract at that bound** ("report what you have"). A subagent that returns partial findings keeps the orchestrator's pipeline alive and lets the coordinator decide whether to re-dispatch with a narrower brief. This is the standard multi-agent pattern: give each subagent an explicit effort budget and require a structured hand-back.

**Why the others fail.**
- **A** — Half the answer. A hard terminate at 10 with no reporting requirement destroys the work done so far and hands the coordinator nothing, so the pipeline stalls instead of degrading gracefully.
- **B** — More context lets it spin *longer*. Context size is not the constraint; convergence criteria are.
- **C** — Collapsing the subagent moves the same unbounded search into the main agent and floods the orchestrator's context with raw search results — the exact problem subagents exist to prevent.

**Source.** [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) · [Claude Code subagents](https://code.claude.com/docs/en/sub-agents)

### UD1-061

**Q.** A loop processes `tool_use` blocks sequentially, one at a time, and is slow when Claude requests multiple tools in a single response. What optimization should they implement?

- A. Execute independent tool calls in parallel.
- B. Queue tool calls and batch them for execution on a fixed schedule.
- C. Increase the API timeout to accommodate the sequential execution time.
- D. Limit Claude to one tool call per response using `tool_choice` to prevent multiple simultaneous requests.

**✅ Answer: A**

**Why it's correct.** Parallel tool use is enabled by default: one assistant message may carry several `tool_use` blocks, and the model emits them together *precisely because* it judged them independent. Execute them concurrently and return **all** the `tool_result` blocks in a **single** user message. (Splitting results across multiple user messages is itself an anti-pattern — it silently trains the model to stop batching.)

**Why the others fail.**
- **B** — Fixed-schedule batching adds latency and machinery to solve a problem concurrency solves directly; the calls are already batched by the model.
- **C** — Raising the timeout hides the symptom and makes each turn slower still.
- **D** — Forcing serial tool use discards the model's own parallelism signal and multiplies round trips — the opposite of the fix.

**Source.** [Implement tool use — parallel tool use](https://docs.claude.com/en/docs/agents-and-tools/tool-use/implement-tool-use) · [Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)

### UD1-071

**Q.** Your agentic loop continues executing even after Claude has signalled completion. What is the correct control-flow condition to terminate the loop?

- A. Terminate when `stop_reason` is `'end_turn'`; continue when `stop_reason` is `'tool_use'`.
- B. Set a maximum iteration count of 10 and terminate when it is reached.
- C. Terminate when the assistant message contains no `tool_use` content blocks.
- D. Terminate when the response text contains phrases such as 'I have completed' or 'Done'.

**✅ Answer: A**

**Why it's correct.** It states the contract exactly and in both directions: `end_turn` → stop, `tool_use` → keep going. Everything else in the loop (caps, timeouts, budget checks) hangs off this as a secondary safety layer.

**Why the others fail.**
- **B** — A cap is a backstop, not a completion condition; alone it both truncates long tasks and over-runs short ones.
- **C** — A derived proxy. It usually coincides with `end_turn`, but silently mishandles `max_tokens`, `pause_turn`, and `refusal` turns, which also contain no `tool_use` blocks yet are not successful completions.
- **D** — Text matching: the canonical anti-pattern (see UD1-049).

### QD1-02

**Q.** *(1.1 | Agentic Loop, stop_reason, Loop Termination | Foundation)* The loop terminates by checking whether the assistant's latest message contains "Task complete". It occasionally fires when the phrase appears inside an explanation. Best fix?

- A. Replace the text-based check with checking `stop_reason == "end_turn"` to determine when to stop the loop.
- B. Add a stricter, less-common phrase (e.g. `===TASK COMPLETE===`) that's less likely to appear accidentally.
- C. Set a maximum iteration cap so the loop terminates safely regardless of text content.
- D. Ask the model to always confirm completion with a structured JSON object at the end of its response.

**✅ Answer: A**

**Why it's correct.** The defect is one of *category*, not *precision*: any signal generated inside the model's free text is probabilistic. `stop_reason` is emitted by the API as protocol metadata and cannot be produced accidentally by prose. Changing the class of signal eliminates the failure mode rather than shrinking it.

**Why the others fail.**
- **B** — Reduces collision probability but keeps a text-based check; the model can still emit the sentinel while quoting instructions or reasoning about the protocol itself.
- **C** — Addresses runaway loops, not premature termination. The stem's bug is stopping *too early*, which a cap cannot prevent.
- **D** — Still model-generated content, plus a parsing step; it can be omitted or malformed. More machinery, same class of unreliability.

### QD1-17

**Q.** *(1.1 | Agentic Loop, stop_reason, Tool Use | Foundation)* On a given turn the response's `stop_reason` is `"tool_use"`. What should the loop do?

- A. Truncate the response since the model ran out of output tokens.
- B. Execute the requested tool call(s), append the results to conversation history as tool results, and send the updated conversation back to the model for another turn.
- C. Treat this as the end of the task and return the response to the user.
- D. Treat this as an error and retry the turn.

**✅ Answer: B**

**Why it's correct.** `"tool_use"` means the model paused specifically to obtain information it cannot produce itself. The handling is fixed: run each `tool_use` block, build a user message containing one `tool_result` per call (matched by `tool_use_id`), append it, re-request.

**Why the others fail.**
- **A** — Running out of output tokens is `stop_reason: "max_tokens"` — a different value with different handling (raise `max_tokens` and retry, or continue).
- **C** — Returning a `tool_use` turn to the user surfaces raw protocol JSON and abandons the task mid-flight.
- **D** — Nothing failed. `"tool_use"` is the normal, expected mid-task state.

### QD1-18

**Q.** *(1.1 | Loop Control, Turn Budget, Spinning Detection | Exam)* 15 turns into a 20-turn budget on a complex refactor; each turn calls a different tool and history keeps growing. How do you decide whether to continue or escalate?

- A. Let it run until the full 20-turn budget is exhausted regardless of content, since turn budgets exist precisely to allow this.
- B. Escalate only if the agent explicitly says it's stuck.
- C. Check whether each turn's tool calls and results represent new information/progress toward the goal, not just whether the turn count is high.
- D. Escalate immediately once past turn 10, since that's over half the budget.

**✅ Answer: C**

**Why it's correct.** Turn count measures *spend*, not *health*. The diagnostic question is whether the loop is progressing: are new files or records being touched, are results changing the plan, is remaining work shrinking? A high turn count on a genuinely complex refactor is fine; a low turn count that repeats the same read is not. Progress-based evaluation is what separates legitimate multi-step work from spinning.

**Why the others fail.**
- **A** — Burns the whole budget on a loop that may have stalled at turn 8, with no early warning.
- **B** — Self-reported stuckness is the least reliable detector; a spinning agent typically believes it is progressing.
- **D** — A fixed fraction of the budget is just another count-based heuristic: it escalates healthy long tasks and misses early stalls.

**Source.** [Building effective agents — knowing when to stop](https://www.anthropic.com/engineering/building-effective-agents) · [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

### QD1-19

**Q.** *(1.1 | Conversation History, Context Window, Pruning | Exam)* A long-running session's history is approaching the model's context window limit after many tool calls. Most reliable fix?

- A. Truncate the oldest turns from the conversation history and never look at them again.
- B. Switch to a model with a larger context window as the permanent fix.
- C. Stop making tool calls once history gets large enough.
- D. Periodically summarize/compact older turns into a condensed representation, preserving only what's still needed for remaining work, rather than keeping every raw tool result.

**✅ Answer: D**

**Why it's correct.** Compaction is *lossy on purpose but selective*: it discards bulky raw tool payloads while carrying forward decisions, constraints, file paths, and open work items. That bounds growth without severing the causal chain the agent depends on. It is what the API's server-side compaction and Claude Code's `/compact` both implement, and it is the recommended pattern for long-horizon agents.

**Why the others fail.**
- **A** — Blind truncation deletes the earliest turns, which usually hold the *task definition and constraints* — the highest-value tokens in the window.
- **B** — Buys headroom without changing the growth rate; any unbounded loop eventually fills any window. It is also a cost and latency regression.
- **C** — Disabling the agent's only means of acting is a capability loss, not a context strategy.

**Source.** [Context windows](https://docs.claude.com/en/docs/build-with-claude/context-windows) · [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### QD1-20

**Q.** *(1.1 | Tool Use, Client Tools, Server Tools | Foundation)* Your agent needs to call an internal, authenticated company API that only your backend can reach. Which tool implementation approach fits?

- A. Define it as a client tool: the model requests the call, but your application code executes it and returns the result.
- B. Define it as a server tool the model executes directly without your application in the loop.
- C. Give the model direct network access so it can call the API itself.
- D. Have the model generate the API call as text for a human to run manually.

**✅ Answer: A**

**Why it's correct.** Client tools (user-defined tools) are exactly this shape: you publish a name, description, and `input_schema`; the model emits a `tool_use` request; **your** process executes it inside your network with your credentials; you hand back a `tool_result`. Secrets never enter the conversation, and the endpoint is reachable because the call originates from your backend.

**Why the others fail.**
- **B** — Server tools are Anthropic-hosted (web search, web fetch, code execution). They run on Anthropic infrastructure, which by definition cannot reach a private internal endpoint, and you cannot register an arbitrary internal API as one.
- **C** — The model has no network stack; there is nothing to grant. Even conceptually this would place credentials in the model's hands.
- **D** — Removes automation entirely. A human step is an approval gate, not a tool implementation.

**Source.** [Tool use overview — client vs. server tools](https://docs.claude.com/en/docs/agents-and-tools/tool-use/overview)

### QD1-21

**Q.** *(1.1 | Loop Control, Escalation, Tool Errors | Exam)* A tool call fails 3 times in a row with the same error, inside a loop with a 10-retry budget still remaining. What should happen?

- A. Immediately terminate the entire session.
- B. Classify the error type first.
- C. Keep retrying until the retry budget is fully exhausted, since budget exists for exactly this.
- D. Silently skip the failed tool call and continue the loop with the next step.

**✅ Answer: B**

**Why it's correct.** Retry policy must be a function of error *class*. A transient error (429, 5xx, timeout, connection reset) warrants continued retry with exponential backoff. A deterministic error (400 bad input, 401/403 auth, 404 missing resource, schema violation) will fail identically on every remaining attempt — retrying wastes the budget and delays escalation. Three identical failures is precisely the signal to stop and classify.

**Why the others fail.**
- **A** — Over-reacts: a transient outage resolves on its own, and killing the session discards all completed work.
- **C** — Treats the budget as a quota to spend rather than a bound not to exceed; guarantees maximum latency and cost on permanently-failing calls.
- **D** — Silent skipping corrupts the result: the model keeps reasoning as though it received data it never got, producing confidently wrong output. Failed calls must be returned as a `tool_result` with `is_error: true` so the model *knows*.

**Source.** [Implement tool use — handling tool errors](https://docs.claude.com/en/docs/agents-and-tools/tool-use/implement-tool-use) · [API errors and retry guidance](https://docs.claude.com/en/api/errors)

### QD1-22

**Q.** *(1.1 | Agentic Loop, Mental Models | Foundation)* How do "perception → reasoning → action → observation" and "gather context → take action → verify work" relate?

- A. The 4-phase framing applies only to single-agent systems and the 3-phase framing only to multi-agent systems.
- B. The 3-phase framing replaced the 4-phase framing as an updated standard.
- C. They describe the same underlying loop at different levels of abstraction.
- D. They are mutually exclusive architectures and a system must choose one.

**✅ Answer: C**

**Why it's correct.** Both describe one cycle. *Perception* and *reasoning* collapse into *gather context*; *action* maps to *take action*; *observation* maps to *verify work*. The 3-phase framing is the practitioner-facing compression of the 4-phase cognitive-architecture framing — useful mainly because "verify" names the step teams most often omit.

**Why the others fail.**
- **A** — Neither framing is scoped by agent count; both apply to a single agent and to each member of a multi-agent system.
- **B** — Not a versioned standard; both remain in current use, often in the same document.
- **D** — There is nothing to choose between: two vocabularies, one control flow.

### QD1-23

**Q.** *(1.1 | Loop Control, Spinning vs Progress | Expert)* An agent repeatedly calls the same search tool with slightly reworded queries across 6 turns without incorporating any new result into its plan. Best characterization and response?

- A. This is legitimate exploration and should be allowed to continue since search tools are inherently iterative.
- B. This is a tool error and the tool itself should be retried with backoff.
- C. This is expected behavior for the perception-reasoning-action-observation loop and requires no intervention.
- D. This is spinning, not legitimate multi-step progress.

**✅ Answer: D**

**Why it's correct.** The defining marker of spinning is *action without integration*: results return and the plan does not change. Reworded queries are the classic signature — the agent varies the surface of its action while its internal state stays fixed. The correct response is intervention: bound the search, inject a directive observation, or escalate.

**Why the others fail.**
- **A** — Legitimate iterative search *narrows*: each result should prune hypotheses or retarget the next query. That is absent here.
- **B** — Nothing errored. The tool returned successfully every time; the failure is in how the agent used the results.
- **C** — The observation phase is precisely what is *not* happening. Calling it expected removes the loop's only self-correction step.

### QD1S-01

**Q.** *(Agentic Loop, stop_reason | Foundation)* A support agent's loop receives `stop_reason: "end_turn"` after calling `get_customer` and `lookup_order` in prior turns. What should the loop do?

- A. Wait for an explicit "done" keyword in the response text before stopping.
- B. Treat this as the model's final response and return it to the user.
- C. Execute the next tool call automatically since the loop must always continue after a tool result.
- D. Treat "end_turn" as an error state and retry the last tool call.

**✅ Answer: B**

**Why it's correct.** `"end_turn"` means the model reached a natural stopping point with nothing further requested. The prior tool calls succeeded and their results are already in context; this turn is the synthesised answer. Return it.

**Why the others fail.**
- **A** — Layers a text check over an authoritative signal, introducing the false-negative hang described in UD1-012.

### QD1S-05

**Q.** *(Loop Control, Safety Backstops | Expert)* A teammate argues: "Since the loop already checks `stop_reason` correctly, the 6-iteration cap serves no purpose and should be removed." Is this reasoning sound?

- A. Yes
- B. No
- C. Yes
- D. No

**✅ Answer: B (No)**

> *Item note:* the options are duplicated (A/C both "Yes", B/D both "No"). The keyed response is the negative — select the first "No".

### BU1-017

**Q.** In an evaluator-optimizer loop, later iterations make only tiny wording changes without improving quality. Which stopping criterion BEST prevents wasted iterations?

- A. Continue until the maximum iteration count is reached regardless of improvement.
- B. Stop once improvements fall below a defined convergence threshold or quality no longer meaningfully increases.
- C. Lower temperature after every iteration so revisions naturally stop changing.
- D. Always run exactly five optimization iterations to keep behavior predictable.

**✅ Answer: B**

**Why it's correct.** The evaluator-optimizer pattern already produces a quality score every round, so the natural stopping rule is *marginal improvement*: halt when the delta falls under a threshold. That aligns spend with value — long on tasks that keep improving, short on tasks that converge quickly — and it directly targets the observed symptom (changes without improvement).

**Why the others fail.**
- **A** — Guarantees the waste described in the stem.
- **C** — Reducing temperature makes revisions *look* stable without any evidence quality improved; it disguises non-convergence rather than detecting it.
- **D** — A fixed count is predictable but arbitrary: it wastes iterations on easy items and truncates hard ones.

### BU1-018

**Q.** An agent that edits files, runs builds, and commits changes sometimes runs 200+ iterations before stopping; it completes, but cost is unpredictable. Which architectural fix BEST addresses this?

- A. Switch from an agent to a deterministic workflow whose fixed five-step plan bounds total cost.
- B. Increase the model's context window so more history fits in a single call.
- C. Add a maximum-iteration cap with an explicit escalation path when the cap is reached.
- D. Remove the build tool so the agent cannot trigger long-running builds.

**✅ Answer: C**

**Why it's correct.** The stated problem is *unpredictable cost*, not incorrect results — the agent completes successfully. A cap converts an unbounded worst case into a known ceiling, and the escalation path ensures hitting that ceiling produces a handled outcome (partial results + human review) instead of a silent failure. It preserves the agent's capability while making spend bounded.

**Why the others fail.**
- **A** — Discards adaptation that the task evidently needs; edit-build-fix cycles cannot be reduced to five fixed steps because the number of fix rounds is data-dependent.
- **B** — Context size is unrelated to iteration count; a larger window makes each expensive iteration cost *more*.
- **D** — Removes the verification step. An agent that edits code without building is faster and much less reliable.

**Source.** [Building effective agents — guardrails and cost control](https://www.anthropic.com/engineering/building-effective-agents)

### BU1-019

**Q.** Which diagram element MOST clearly identifies a system as agentic rather than a workflow?

- A. A user box at the top connected straight down to a response box at the bottom.
- B. A box labeled 'Claude' connected by a directed arrow to a box labeled 'Tool'.
- C. Multiple tool boxes connected in sequence.
- D. An arrow from tool output back into the model's input as part of the next iteration.

**✅ Answer: D**

**Why it's correct.** The **feedback edge** is the signature. An arrow returning tool output into the model's input means the model observes the result and chooses the next action from it — the loop. Without that edge you have a pipeline, however many tools it contains.

**Why the others fail.**
- **A** — A straight user → response path is the conversational class: no tools, no loop.
- **B** — A one-way Claude → Tool arrow is plain tool use: a call with no observation edge.
- **C** — Tools in sequence is a workflow: the order is fixed in the diagram, therefore predetermined rather than chosen at runtime.

**Source.** [Building effective agents — architecture diagrams](https://www.anthropic.com/engineering/building-effective-agents)

### CS1-001

**Q.** A research agent keeps spawning follow-up searches and the run is not converging. The most reliable way to prevent an endless loop is to:

- A. Let it continue until it naturally stops.
- B. Give the task an explicit budget and a coverage check, and stop once the questions are answered or the budget is spent.
- C. Cut the run off at a random time.
- D. Add more sub-agents so it finishes sooner.

**✅ Answer: B**

**Why it's correct.** Two complementary stopping conditions: a **coverage check** (goal-relative — have the research questions been answered?) which stops the run as soon as it is genuinely done, and a **budget** (resource-relative) which bounds the worst case when coverage is never reached. Together they terminate on success *and* on failure, which is what "reliable" requires.

**Why the others fail.**
- **A** — Restates the failing behaviour; the stem says it does not naturally stop.
- **C** — A random cutoff is a bound with no relationship to progress: it truncates converging runs and lets others run long.
- **D** — Parallelising an unconverged search multiplies cost and adds a synthesis burden; it does not supply a stopping condition.

### CS1-002

**Q.** When the agent calls `lookup_order` and receives details showing the item was purchased 45 days ago, how does the agentic loop determine whether to call `process_refund` or `escalate_to_human` next?

- A. The orchestration layer automatically routes to the next tool based on the order's status field.
- B. The agent follows a pre-configured decision tree mapping order attributes to specific tool calls.
- C. The order details are added to the conversation and the model reasons about which action to take.
- D. The agent executes the remaining steps in a tool sequence planned at the start of the request.

**✅ Answer: C**

**Why it's correct.** This is the mechanism of the loop. The tool result is appended as a `tool_result` block in the conversation; on the next request the model reads it *in context*, applies the policy in its system prompt (e.g. "refunds within 30 days, otherwise escalate"), and emits the corresponding `tool_use` block. The decision lives in the model's reasoning over conversation state, not in the harness.

**Why the others fail.**
- **A** — The orchestration layer transports results and executes requested calls; it does not inspect payload fields to pick the next tool. If it did, the system would be a workflow.
- **B** — A pre-configured decision tree is again a workflow. Nothing in the agentic loop consults such a structure.
- **D** — Contradicts the loop: the plan is not fixed at request start. Had a full sequence been planned up front, the 45-day fact could not have influenced anything.
