## 5.1 — Context preservation in long interactions

**Governing principles for this section.**
1. **Compaction is selective, not lossy-by-default.** Summarise resolved material; preserve verbatim what is still live; and lift critical facts (IDs, amounts, dates, decisions) into a **persistent structured block** that survives every compaction cycle.
2. **"Lost in the middle" is an attention problem.** Fix it with structure — key findings first, explicit headings, chunking — not with a bigger window.
3. **Compress at the source.** A subagent returning structured findings instead of raw page content prevents the overflow rather than summarising it away later.
4. **Everything counts toward the window**: input, output, images, thinking tokens, tool results.
5. **Statelessness is the default.** Conversation history is re-sent on every request; nothing persists between sessions unless you persist it.

### UD5-002

**Q.** An agent loop appends tool results to history; after 20 iterations the context window approaches its limit. How do you manage conversation history in long-running loops?

- A. Increase context window size to accommodate all iterations without truncation.
- B. Clear conversation history periodically, restarting the agent with fresh context.
- C. Implement a sliding window maintaining context relevance, summarizing older content.
- D. Truncate the oldest tool results, keeping only recent results.

**✅ Answer: C**

**Why it's correct.** A sliding window **with summarisation** bounds growth while preserving the causal chain: recent turns stay verbatim (where detail matters most), older material is condensed into what still bears on the remaining work, and nothing is silently dropped. This is the pattern behind both server-side compaction and `/compact`.

**Why the others fail.**
- **A** — Buys headroom without changing the growth rate; any unbounded loop fills any window.
- **B** — Clearing discards the task definition and everything learned, so the agent restarts from nothing.
- **D** — Truncating the oldest results removes the earliest turns, which typically hold the goal and constraints — the highest-value tokens present.

**Source.** [Context windows and compaction](https://docs.claude.com/en/docs/build-with-claude/context-windows) · [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

### UD5-004

**Q.** Long-document extraction shows the "lost in the middle" effect — middle content is missed despite being within the context window. How do you address attention dilution?

- A. Use extended thinking, giving the model more time for complete analysis.
- B. Explicit instructions directing attention to middle sections.
- C. Increase context window size, reducing the "middle" proportion of the document.
- D. Split the document into focused chunks, processing each independently with overlap.

**✅ Answer: D**

**Why it's correct.** Chunking **eliminates the middle**: in a small enough chunk, every position is effectively a high-attention position. The overlap matters too — it ensures information spanning a boundary appears intact in at least one chunk, so nothing is lost at the seams.

**Why the others fail.**
- **C** — The stem already says the content is *within* the window; a larger window leaves the same proportion in the middle, just of a bigger document.
- **A** — Thinking time does not change where attention falls across a long input.
- **B** — "Pay attention to the middle" is an instruction against an architectural effect; it cannot reliably override it.

**Source.** [Long context prompting tips](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/long-context-tips) · [Context windows](https://docs.claude.com/en/docs/build-with-claude/context-windows)

### UD5-016

**Q.** Web-search output (85K tokens **including page content**) plus document-analysis output (70K **including chains of thought**) totals 155K, but the synthesis agent performs best under 50K. Most effective solution?

- A. Have the synthesis agent process findings in sequential batches, maintaining state between calls.
- B. Modify upstream agents to return structured data (key facts, quotes, relevance scores) instead of verbose content and reasoning.
- C. Store findings in a vector database and give synthesis search tools to query during its work.
- D. Add an intermediate summarization agent that condenses findings before synthesis.

**✅ Answer: B**

**Why it's correct.** The stem tells you what the bulk *is*: raw page content and reasoning traces — material the synthesis agent does not need. **Fixing the contract at the source** eliminates the tokens rather than compressing them later, and structured output (facts, quotes, scores) is more useful to synthesis than prose ever was. It also costs nothing extra: no additional agent, no additional call.

**Why the others fail.**
- **D** — The closest alternative, and it works — but it adds a whole agent and a pass over 155K tokens to discard material that should never have been produced.
- **A** — Batching means synthesis never sees all findings together, which is exactly what synthesis requires.
- **C** — Retrieval is lossy and non-deterministic for a task that needs *all* findings; a missed query silently drops a source.

**Source.** [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) · [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

### UD5-018

**Q.** An MCP database tool returns 500 rows as 200K tokens. Following MCP design best practices, what should the tool return?

- A. The full 200K token result so Claude has complete information.
- B. Only the first row as a sample with total row count.
- C. A compressed binary representation.
- D. A summary with row count, column names, first 10 rows as examples, and a pagination token for fetching more rows on demand.

**✅ Answer: D**

**Why it's correct.** It gives the model everything needed to **decide what to do next** — how many rows matched, what the shape of the data is, what the values look like — at a tiny fraction of the tokens, plus a pagination token so the full data remains reachable on demand. Nothing is lost; it is deferred.

**Why the others fail.**
- **A** — 200K tokens for one tool call would consume most of the window and crowd out the task.
- **B** — One row and a count is too little: no column names, no sense of the data's variety, and no way to fetch more.
- **C** — Compression does not reduce token count once decoded, and the model cannot read a binary blob.

**Source.** [Writing tools for agents — token efficiency](https://www.anthropic.com/engineering/writing-tools-for-agents) · [MCP — tools](https://modelcontextprotocol.io/docs/concepts/tools)

### UD5-019

**Q.** 80,000 documents each needing one classification call; results are needed for a report generated **every Friday**. Most cost-effective approach?

- A. Real-time API calls with prompt caching.
- B. Message Batches API submitted Thursday with results available within 24 hours for Friday's report.
- C. Real-time API calls processed sequentially throughout the week.
- D. Multiple small batch jobs submitted daily throughout the week.

**✅ Answer: B**

**Why it's correct.** The deadline is **weekly**, so a 24-hour processing window is comfortably within tolerance — which makes this the textbook Batch API case and captures the ~50% discount on all 80,000 calls. Submitting Thursday for Friday leaves the full window available.

**Why the others fail.**
- **A** — Caching helps with repeated prefixes but does not approach the batch discount, and real-time pricing applies to every call.
- **C** — Full price, plus a week of sequential processing.
- **D** — Also uses the Batch API, so it captures the discount, but daily submission adds orchestration and tracking for no benefit when nothing is needed before Friday.

### UD5-020

**Q.** 60% of cost is input tokens (mostly repeated context), 15% output, 25% thinking. Which optimization provides the biggest reduction?

- A. Reduce output length with `max_tokens` to save on the 15%.
- B. Switch to a smaller model with lower per-token costs.
- C. Reduce thinking budget to save on the 25%.
- D. Implement prompt caching to save on the 60%.

**✅ Answer: D**

**Why it's correct.** Two facts point the same way: input is the **largest** cost category, and the content is **repeated** — which is precisely the condition under which caching pays, since cache reads are billed at a large discount. Attacking the biggest line item with the mechanism designed for its exact shape gives the largest saving with no capability loss.

**Why the others fail.**
- **A** — Optimises the smallest category, and truncating output degrades results.
- **C** — Cuts reasoning quality on a quarter of spend when the larger, cost-free saving is available.
- **B** — Reduces every rate but lowers capability across the board; a capability decision should not be driven by a cost problem that caching solves.

### UD5-021

**Q.** A 48-turn session covering a refund inquiry, subscription question, and payment update is approaching context limits. Optimal **compression strategy**?

- A. Switch to a model with a larger context window.
- B. Summarise the entire session into a single paragraph and continue.
- C. Summarise earlier, **resolved** issues into a narrative description while preserving full verbatim history only for the **active, unresolved** issue.

**Why the others fail.**
- **B** — A single paragraph for three issues loses the active issue's detail, which is the part that must be preserved.
- **D** — Deletes by position rather than relevance; the oldest 20 turns may contain the active issue's origin.
- **A** — Not a compression strategy, and it postpones rather than solves.

### UD5-022

**Q.** A "turn" in the Agent SDK makes multiple Claude API calls with tool use. Which metric tracks how many iterations the agent performed?

- A. The number of `tool_use` blocks generated across all responses.

### UD5-024

**Q.** A long-running agent has a stable system prompt and first few turns, with frequently-changing recent messages. Where should explicit cache breakpoints go?

- A. On every message to cache as much as possible.
- B. On the most recent messages to cache the newest content.
- C. On the last stable content block before the frequently changing messages, with up to 4 explicit breakpoints on stable blocks.
- D. Only on the system prompt, since tool definitions shouldn't be cached.

**✅ Answer: C**

**Why it's correct.** Caching is **prefix-based**, so a breakpoint is only useful where everything before it is byte-identical across requests. Placing it at the boundary between the stable region and the volatile region maximises the cached prefix; the 4-breakpoint limit is the documented maximum.

**Why the others fail.**
- **B** — Caches content that changes next request, so it is never read back.
- **A** — Exceeds the breakpoint limit, and breakpoints inside the volatile region are wasted.
- **D** — Tool definitions render *first* in the prefix and are usually the most stable, largest block — excluding them forfeits the biggest saving.

**Source.** [Prompt caching](https://docs.claude.com/en/docs/build-with-claude/prompt-caching)

### UD5-027

**Q.** Combining prompt caching with compaction: after compaction creates a summary block, subsequent requests show **no cache hits** even though the system prompt is unchanged. Explanation?

- A. Cache TTL expired during compaction processing.
- B. The compaction block itself needs a `cache_control` breakpoint to establish a new cache entry subsequent requests can match against.
- C. Compaction is incompatible with prompt caching.
- D. The compaction block is too large for the minimum cacheable threshold.

**✅ Answer: B**

**Why it's correct.** Compaction **rewrites the message history**, so the prefix that follows the system prompt is entirely new — and because caching matches on a contiguous prefix, the old cache entry no longer applies from that point on. The fix is to mark a new breakpoint after the compaction block so a fresh cache entry is established for the new prefix.

**Why the others fail.**
- **C** — They compose fine; the interaction just has to be handled.
- **D** — Inverts the threshold: it is a *minimum* size, and being large helps rather than hinders.
- **A** — TTL expiry would be time-dependent and intermittent, not consistently correlated with compaction.

### UD5-028

**Q.** With server-side compaction, an architect wants to inject additional context (e.g. updated tool results) **after** compaction but **before** the conversation continues. Which configuration enables this?

- A. Set `instructions` in the compaction config to include the additional context in the summary.
- B. Append additional context as a system message after receiving the compaction block.
- C. Use a PreCompact hook to inject context before compaction occurs.
- D. Configure `pause_after_compaction: true`, which returns `stop_reason: 'compaction'`, allowing context injection before continuing.

**✅ Answer: D**

**Why it's correct.** It creates the **control point** the requirement needs: compaction completes, the request returns with a distinguishable stop reason, and your code injects whatever it wants before issuing the next request. Timing is exactly "after compaction, before continuation".

**Why the others fail.**
- **C** — PreCompact runs *before* compaction, so injected content would itself be summarised away — the wrong side of the boundary.
- **A** — Compaction instructions shape how existing history is summarised; they cannot introduce new tool results.
- **B** — Appending after the fact without pausing means the model has already continued; the injection misses the turn it was meant to inform.

### UD5-030

**Q.** An agentic loop encounters `stop_reason: 'max_tokens'` after requesting a complex analysis. What does it indicate and what should be done?

- A. Claude's response was truncated due to the token limit.
- B. The context window is full.
- C. Claude wants to call a tool but the response was cut off.
- D. Claude has finished its analysis.

**✅ Answer: A**

**Why it's correct.** `max_tokens` means generation stopped at the **output limit**, so the response is incomplete. The remedy is to raise `max_tokens` (using streaming for large values), or to break the analysis into smaller requests — and critically, **not** to treat the partial output as a finished answer.

**Why the others fail.**
- **B** — A full context window produces a different error at request time, not this stop reason.
- **D** — `end_turn` signals completion; `max_tokens` is the opposite.
- **C** — Speculates about intent the stop reason does not convey; a truncated turn may or may not have been heading toward a tool call.

### UD5-031

**Q.** 8K system prompt, 5 tool definitions at 2K each, user messages averaging 500 tokens, responses up to 4K, on a 200K model. Approximately how many turns before hitting the limit?

- A. About 180 turns · **B.** About 20 turns · **C.** About 40 turns · **D.** Unlimited, because old messages are truncated automatically

**✅ Answer: C**

**Why it's correct.** The arithmetic:

| Component | Tokens |
|---|---|
| System prompt | 8,000 |
| 5 tools × 2,000 | 10,000 |
| **Fixed overhead** | **18,000** |
| Remaining budget | 200,000 − 18,000 = **182,000** |
| Per turn (500 user + 4,000 response) | **4,500** |
| Turns | 182,000 ÷ 4,500 ≈ **40** |

The key insight is that the fixed overhead is paid **once**, while each turn's tokens **accumulate** in history and are re-sent on every subsequent request.

**Why the others fail.**
- **A** — ~180 would follow from counting only the 500-token user messages, ignoring the 4K responses that dominate.
- **B** — ~20 would follow from charging the 18K overhead per turn rather than once.
- **D** — Nothing truncates automatically; exceeding the window is an error unless you implement compaction.

**Source.** [Context windows](https://docs.claude.com/en/docs/build-with-claude/context-windows) · [Token counting](https://docs.claude.com/en/docs/build-with-claude/token-counting)

### UD5-032

**Q.** After compaction, specific numerical values from early in the conversation (balances, dates, transaction IDs) are lost in the summary. What design pattern prevents this?

- A. Increase the compaction trigger threshold to delay summarization.
- B. Disable compaction and rely on larger context windows.
- C. Custom compaction instructions specifically requesting preservation of numerical values.
- D. Extract critical transactional facts into a **persistent structured block** that survives compaction.

**✅ Answer: D**

**Why it's correct.** Summarisation is inherently lossy on specifics, so the durable fix is to move those facts **out of the summarisable region entirely**. A persistent structured block is carried forward verbatim through every compaction cycle, so a transaction ID recorded at turn 3 is still exact at turn 300.

**Why the others fail.**
- **C** — The plausible runner-up, and worth doing — but instructions to a summariser are probabilistic, so values will still be lost sometimes. "Prevents" requires the structural guarantee.
- **A** — Delays the loss to a later compaction rather than preventing it.
- **B** — Removes the mechanism that keeps long sessions viable, and hits the same wall later.

### UD5-038

**Q.** Documenting a 500,000-line codebase by summarising each module and discarding its source. After 20 modules, docs for module 21 reference class names from module 3 that were **renamed in module 12**. What caused this?

- A. Progressive summarisation lost the rename detail: when module 12's summary replaced its source, the rename was condensed to "various refactoring changes", so the agent retained module 3's original class names from its earlier summary.
- B. The context window overflowed, causing hallucinated class names.
- C. Claude Code cached module 3's source and served the stale version instead of the updated file.
- D. The model confused similar class names because too many modules were processed in one session.

**✅ Answer: A**

**Why it's correct.** It traces the exact failure path. Module 3's summary — recorded before the rename — carried the old names. Module 12's summary was *supposed* to record the rename, but summarisation compressed away the specific old→new mapping. The agent is now working from two summaries, one stale and one that omitted the correction, and has no source to fall back on because it was discarded. This is UD5-032's lesson applied to a real workflow: **cross-cutting facts like renames must be persisted structurally**, not left to per-module summaries.

**Why the others fail.**
- **B** — Overflow would raise an error, and the names are not hallucinated — they were real, at module 3.
- **C** — No such stale-source caching, and the summaries, not the files, are what the agent is reading.
- **D** — Not confusion between similar names; the agent is confidently using a name that was correct earlier.

### UD5-039

**Q.** What happens when a project knowledge base approaches context limits?

- A. Claude stops accepting new file uploads.
- B. Older files are automatically deleted to make room.
- C. You must create a new project to continue.
- D. Claude searches your project knowledge and retrieves only what's relevant, expanding capacity by up to 10×.

**✅ Answer: D**

**Why it's correct.** Beyond a threshold the project switches from loading everything into context to **retrieving what is relevant per request**. Because only the pertinent material is loaded each time, the effective capacity of the knowledge base grows substantially without any of it being discarded.

**Why the others fail.**
- **A** and **C** — Both describe hard limits; the system degrades gracefully instead.
- **B** — Nothing is deleted; retrieval changes what is *loaded*, not what is *stored*.
