# Domain 4 — Prompt Engineering & Structured Output — Answer Key

**Source pool:** `../D4.md` (87 questions across 6 task statements)
**Each entry contains:** the question, the options, the correct answer, why it is correct, why every distractor fails, and the authoritative source.

> **How to read this key.** `✅` marks the keyed answer. Two distractor families recur throughout this domain and are almost always wrong: **"lower the temperature"** (sampling variance is not a substitute for a specification) and **emphasis words** ("be thorough", "very important") added to a vague instruction. The real question is usually *which* mechanism — explicit criteria, few-shot examples, a schema constraint, or a validation gate — fits the failure you actually have.

---

## 4.1 — Explicit criteria and false positives

**Governing principles for this section.**
1. **Vague instruction → make it explicit.** Name the exact format, the exact trigger, the exact forbidden action. "Be thorough" specifies nothing.
2. **Explicit criteria already tried and still failing → move to few-shot with borderline cases.** Judgement boundaries are demonstrated better than they are described. Which of these two applies is the discriminator on several items here.
3. **Never summarise transactional facts.** Amounts, dates, IDs, and names are preserved verbatim; approximation is data loss.
4. **Trust is per-category.** A high false-positive category poisons confidence in accurate ones, so disabling it can improve the system's effective value even though it removes findings.
5. **Missing data is reported as missing** — `null` plus a not-found marker — never inferred, and never a reason to fail the whole extraction.

### UD4-003

**Q.** A prompt extracts invoice data (amount $1,247.83, date 2024-03-15, vendor Acme Corp) but the agent summarizes as "approximately $1,200 mid-March from vendor". What principle prevents lossy summarization?

- A. Validation checking extracted data matches source document exactly.
- B. Schema constraints enforcing specific formats for amounts and dates.
- C. Never summarize transactional facts: preserve exact amounts, dates, IDs, names.
- D. More explicit instructions emphasizing precise extraction without summarization.

**✅ Answer: C**

**Why it's correct.** The question asks for the **principle**, and this is it: extraction is a *copying* operation, not a *describing* one. Transactional facts have no acceptable paraphrase — "approximately $1,200" is not a lossy version of $1,247.83, it is a different and unusable value, and the same holds for dates and identifiers.

**Why the others fail.**
- **A** — Validation is a *detective control* that catches violations of the principle; it presupposes the principle rather than stating it.
- **B** — Schema constraints enforce the *shape* of a value (a decimal, an ISO date) but cannot detect that a correctly-shaped number is the wrong one.
- **D** — Emphasis on an instruction that is already being disobeyed; it names no principle.

**Source.** [Prompt engineering — be clear and direct](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/be-clear-and-direct) · [Structured outputs](https://docs.claude.com/en/docs/build-with-claude/structured-outputs)

### UD4-006

**Q.** Automated code review in CI/CD has a high false-positive rate; **detailed criteria in the prompt doesn't reduce them**. Which technique reduces false positives?

- A. More explicit criteria defining exactly what constitutes a legitimate issue.
- B. Multiple review passes with a voting mechanism.
- C. Increase confidence threshold, requiring high-confidence findings only.
- D. Few-shot examples showing borderline cases with reasoning about accept vs reject.

**✅ Answer: D**

**Why it's correct.** The stem's key clause is that **detailed criteria have already failed**. False positives cluster at the *boundary* between "real issue" and "acceptable code", and that boundary resists description — but it is demonstrable. Borderline examples *with the reasoning attached* teach the discrimination directly: this looks like a problem and is not, and here is why.

**Why the others fail.**
- **A** — Explicitly ruled out by the stem; more of what is not working.
- **B** — Voting over N passes that share the same faulty boundary reproduces the same false positives at N× cost.
- **C** — Raising the threshold suppresses low-confidence findings indiscriminately, discarding true positives along with false ones. It trades recall for precision rather than improving the judgement.

**Source.** [Multishot prompting](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/multishot-prompting) · [Prompt engineering overview](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/overview)

### UD4-015

**Q.** Automated code review has a 40% false-positive rate; **detailed review criteria in the prompt doesn't reduce it**. Which technique reduces the rate?

- A. Few-shot examples showing borderline cases with reasoning about accept versus reject.
- B. Increase confidence threshold, requiring only high-confidence findings.
- C. More explicit review criteria defining exactly what constitutes legitimate issues.
- D. Multiple review instances with a voting mechanism for consensus.

**✅ Answer: A**

**Why it's correct.** Identical to UD4-006: criteria have been tried and failed, so the remedy is demonstrating the boundary rather than describing it. At a 40% false-positive rate the boundary is badly miscalibrated, and worked borderline cases with reasoning are what recalibrate it.

**Why the others fail.**
- **C** — Ruled out by the stem.
- **B** — Suppresses findings by confidence rather than correcting the judgement, losing true positives too.
- **D** — Consensus among instances sharing the same miscalibration is agreement, not accuracy.

### UD4-024

**Q.** During a long debugging session the agent starts giving vague, generic responses ("this follows typical patterns") instead of referencing specific classes and methods it examined earlier. What is happening and what should be done?

- A. The model's temperature is increasing over time.
- B. The model is rate-limited.
- C. The agent needs more explicit instructions.
- D. Context degradation from an extended session.

**✅ Answer: D**

**Why it's correct.** The symptom is diagnostic: responses become **generic precisely where they were previously specific**, which is what happens as earlier detail is crowded out or diluted in a long, accumulating context. The remedy is context management — compact with a summary that preserves the key findings, or start a fresh session seeded with them (Domain 1, §1.7).

**Why the others fail.**
- **A** — Temperature is a fixed request parameter; it does not drift during a session.
- **B** — Rate limiting produces 429 errors, not degraded content.
- **C** — Instructions cannot recover specifics no longer effectively available in context; adding them consumes more of the resource that is already scarce.

**Source.** [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) · [Long context prompting tips](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/long-context-tips)

### UD4-029

**Q.** Inconsistent severity ratings, growing developer distrust ("half are wrong"), and high-false-positive categories eroding trust in accurate ones. Which approach best restores developer trust while improving the system?

- A. Keep all categories enabled and add few-shot examples to improve accuracy over the next few weeks.
- B. Temporarily disable high-false-positive categories (style, naming, documentation) and keep only high-precision categories while improving prompts.
- C. Keep all categories enabled but display confidence scores so developers decide what to investigate.
- D. Apply a uniform strictness reduction across all categories.

**✅ Answer: B**

**Why it's correct.** Trust is the binding constraint, and it is **contaminated across categories** — developers dismissing findings unread means even accurate security findings go unactioned. Disabling the noisy categories immediately raises observed precision, so the remaining findings are worth reading; "temporarily … while improving prompts" preserves the path back. It fixes trust now and quality in parallel.

**Why the others fail.**
- **A** — Correct long-term work, wrong sequencing: trust keeps eroding for the weeks it takes, and by then developers have stopped reading.
- **C** — Confidence scores shift the filtering burden onto the developers who have already opted out of reading; a low-confidence finding is still noise in the queue.
- **D** — Uniform reduction lowers sensitivity on the 8% -false-positive security category too, suppressing exactly the findings that are trustworthy.

**Source.** [Building effective agents — evaluation](https://www.anthropic.com/engineering/building-effective-agents) · [Prompt engineering overview](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/overview)

### UD4-051

**Q.** Which three elements make up an effective prompt?

- A. Introduction, body, and conclusion.
- B. Setting the stage, defining the task, and specifying rules.
- C. Question, answer, and follow-up.
- D. Subject, verb, and object.

**✅ Answer: B**

**Why it's correct.** The three elements map to the three things a model needs: **context** (role, audience, background — setting the stage), **the task** (what specifically to produce), and **constraints** (format, tone, length, prohibitions). Omitting any one is where most prompt failures in this section originate.

**Why the others fail.**
- **A** — Essay structure, describing a document's shape rather than a prompt's components.
- **C** — Conversation structure; the answer is what you are asking *for*, not part of the prompt.
- **D** — Sentence grammar, unrelated.

**Q.** If Claude's response is too generic, what should you try?

- A. Switch to a different AI model.
- B. Ask Claude to search the web for better answers.
- C. Add more details about your audience, role, or constraints.

- **A** — A more capable model still cannot know an audience you have not named.

### UD4-053

**Q.** A good Cowork prompt typically names which three things?

- A. The deliverable you want, the inputs to use, and any nuance like audience or format.
- B. Your name, your team, and your deadline.
- C. The model, the temperature, and the token limit.

**Why the others fail.**

- **D** — Politeness, which changes nothing about the output.

### BU4-001

**Q.** "Generate idiomatic SQL queries" yields inconsistent style — keyword casing and column quoting vary. Which change MOST directly stabilizes style?

- A. Name the style guide explicitly.
- B. Raise temperature so style varies less from query to query.
- C. Provide one example query and instruct the model to match its keyword casing and quoting.
- D. Use prefilling to start each response with `SELECT ` so the style is anchored early.

**✅ Answer: A**

**Why it's correct.** "Idiomatic" is undefined — several mutually incompatible SQL conventions are all idiomatic, so the model picks one each time. Naming the specific guide (or spelling out its rules: uppercase keywords, double-quoted identifiers) replaces an underspecified word with a **complete, unambiguous standard** that covers cases no single example would.

**Why the others fail.**
- **C** — The reasonable runner-up, and it would help — but one example demonstrates only the constructs it happens to contain, leaving JOINs, CTEs, and window functions unspecified. A named guide covers all of them.
- **B** — Backwards: higher temperature *increases* variance. (And sampling variance is not the cause; underspecification is.)
- **D** — Prefilling anchors one token and says nothing about identifier quoting or the rest of the query — and assistant prefill is rejected on current models.

**Source.** [Prompt engineering — be clear and direct](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/be-clear-and-direct) · [System prompts](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/system-prompts)

### BU4-002

**Q.** "Fetch the most relevant 5 sources" yields sources that sometimes overlap heavily. Which change BEST improves source diversity?

- A. Increase the source count to 10 so diversity emerges naturally.
- B. Require sources to cover distinct viewpoints.
- C. Raise temperature so source selection is more varied.
- D. Sort sources alphabetically and take the first five for reproducibility.

**✅ Answer: B**

**Why it's correct.** The prompt optimises for **relevance alone**, and the five most relevant sources are frequently near-duplicates of each other — the overlap is the criterion working as specified. Adding diversity as an explicit selection criterion changes what "best five" means, so the model optimises for coverage as well as relevance.

**Why the others fail.**
- **A** — Ten sources selected by the same criterion gives ten overlapping sources; volume does not create coverage.
- **C** — Randomness is not diversity: it produces varied *runs*, not varied *viewpoints within a run*, and degrades relevance.
- **D** — Alphabetical order is unrelated to either relevance or diversity; reproducibly bad.

**Source.** [Prompt engineering — be clear and direct](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/be-clear-and-direct) · [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)

### BU4-003

**Q.** The agent should reply in Spanish when the user writes in Spanish, but sometimes replies in English or code-switches. Which change MOST directly enforces language matching?

- A. Add "always be linguistically appropriate" so the model self-corrects.
- B. Run a language-detection step in a separate API call first.
- C. Lower temperature to 0 so the language choice becomes deterministic.
- D. Rule: detect the dominant language of the user's most recent message and respond entirely in that language unless the user explicitly requests another.

**✅ Answer: D**

**Why it's correct.** It converts a vague intent into a **complete decision procedure**: which signal to read (the most recent message), how to resolve mixed input (the *dominant* language — which is what fixes code-switching), what to output (entirely that language), and the one exception. Nothing is left to interpretation.

**Why the others fail.**
- **A** — "Linguistically appropriate" is vaguer than the original instruction.
- **B** — An extra API call, extra latency, and its own error rate, to determine something the model can determine inline.
- **C** — Temperature 0 makes the *same wrong choice* consistently; determinism is not correctness.

**Source.** [Prompt engineering — be clear and direct](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/be-clear-and-direct)

### BU4-004

**Q.** "Extract dates in ISO format" yields `2026-06-15`, `2026/06/15`, and `June 15 2026`. Which change BEST stabilizes the format?

- A. Use JSON mode so the date is emitted as a clean string value.
- B. Provide three examples of ISO dates and trust the model to generalize.
- C. Lower temperature so the date-format choice stabilizes.
- D. Specify "YYYY-MM-DD with hyphens, zero-padded; reject any other format" and provide one canonical example.

**✅ Answer: D**

**Why it's correct.** It removes every degree of freedom the failures exploited: the **separator** (hyphens, which kills the `/` variant), **zero-padding**, the exact field order, and an explicit rejection of alternatives — plus one example to anchor it. Rule *and* demonstration, which is stronger than either alone.

**Why the others fail.**
- **B** — Three examples without a stated rule leave the model to infer which properties are essential; and the item's own phrasing ("trust the model to generalize") is the weakness.
- **A** — JSON mode guarantees the value is a valid *string*; `"June 15 2026"` is a perfectly valid JSON string.
- **C** — Determinism without a specification just fixes which wrong format recurs.

### BU4-005

**Q.** A system prompt has 8 imperative instructions, with new rules appended at the bottom over time. Which change BEST improves long-term maintainability?

- A. Convert the imperatives to declaratives so they read more naturally.
- B. Number the rules so each can be referenced by a stable index.
- C. Group related rules under XML-tagged sections.
- D. Lower temperature so the rules are applied more consistently.

**✅ Answer: C**

**Why it's correct.** The maintainability problem is **structural**: an append-only flat list means related rules drift apart, duplicates go unnoticed, and there is no obvious place to add the next one. XML-tagged sections give each rule a home (`<style>`, `<testing>`, `<security>`), which both guides future edits and improves the model's ability to attend to the relevant group — XML structuring is a documented Claude prompting technique, not merely cosmetic.

**Why the others fail.**
- **B** — Stable indices help *reference* rules but do nothing to organise them; and inserting a rule renumbers everything after it.
- **A** — Imperatives are the clearer form for instructions; declaratives read as description rather than requirement.
- **D** — Temperature is unrelated to maintainability, and this is the recurring non-answer of this domain.

**Source.** [Use XML tags](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/use-xml-tags) · [System prompts](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/system-prompts)

### BU4-006

**Q.** "Refactor for readability while keeping behavior the same" — some refactors silently change function signatures. Which change MOST directly prevents signature changes?

- A. Lower temperature to 0 so refactors become more conservative.
- B. Explicitly forbid signature changes.
- C. Run the refactor through a linter after Claude finishes.
- D. Use prefilling to start with `def ` and the original function name.

**✅ Answer: B**

**Why it's correct.** "Behavior the same" is genuinely ambiguous — a model can read it as *observable behaviour for a given call*, under which renaming a parameter seems harmless. Naming the prohibition explicitly closes that reading, and it is the most direct fix because it addresses the exact misinterpretation causing the failures. (BU4-013 restates this item with the full wording spelled out.)

**Why the others fail.**
- **C** — A linter checks style; it has no notion of the *original* signature to compare against, so it cannot detect the change.
- **A** — Temperature does not make a model "conservative"; it narrows sampling around the same interpretation.
- **D** — Prefill is rejected on current models, and anchoring the first line would not prevent a changed parameter list further along it.

### BU4-007

**Q.** "Write a good README" — some include installation but skip usage, others include badges but no quickstart. Which change MOST efficiently fixes the gaps?

- A. Require a fixed section order.
- B. Show Claude five high-quality READMEs from popular projects.
- C. Lower temperature so the README structure stabilizes.
- D. Add "be thorough and complete" so no section is skipped.

Note "MOST **efficiently**": this is a few lines of prompt, not five documents.

**Why the others fail.**

- **D** — "Thorough" is exactly the vagueness that produced inconsistent coverage.

### BU4-008

**Q.** "Verify the customer's identity before sharing account details" — the model sometimes shares partial details without verification. Which change BEST hardens the rule?

- A. Lower temperature so the model is less likely to share details prematurely.
- B. Add "verify thoroughly and completely" to the existing prompt.
- C. Specify the verification steps.
- D. Wrap account details in an `<account>` XML tag in the response.

**✅ Answer: C**

**Why it's correct.** "Verify identity" names an outcome without a procedure, so the model has to decide what counts as verified — and "partial details" suggests it is treating partial confirmation as sufficient. Enumerating the steps ("confirm account number **and** registered email; both must match before any detail is disclosed") makes the precondition checkable rather than judged.

> **Worth knowing beyond this item:** for a genuine guarantee on a security-sensitive action, the prompt layer is the wrong layer entirely — a programmatic prerequisite gate is (Domain 1, §1.4, UD1-008). Among the options offered here, C is the strongest, but a real system should gate `share_account_details` on a completed verification call.

**Why the others fail.**
- **B** — Adverbs on an unspecified procedure.
- **A** — Temperature does not encode a policy.
- **D** — Tags the output after the disclosure decision was already made.

**Source.** [Prompt engineering — be clear and direct](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/be-clear-and-direct) · [Claude Code hooks](https://code.claude.com/docs/en/hooks)

### BU4-009

**Q.** Merge recommendations vary between "merge" and "consider merging"; reviewers want a binary decision. Which change BEST enforces a binary verdict?

- A. Add "be decisive and commit to a single verdict".
- B. Lower temperature to 0 so the recommendation is more confident.
- C. Require the response to end with exactly one of: `VERDICT: MERGE` or `VERDICT: HOLD`.
- D. Use prefilling to start the response with "I recommend".

**✅ Answer: C**

**Why it's correct.** It replaces a request for decisiveness with a **format constraint that has no hedging form**: there is no way to emit `VERDICT: MAYBE`. The fixed token also makes the verdict machine-parseable, which is what a CI gate needs — the response can still explain its reasoning above the line.

**Why the others fail.**
- **A** — "Be decisive" is an adverb on the same open-ended output; "consider merging" can be delivered decisively.
- **B** — Determinism produces a *consistent* hedge, not a binary one.
- **D** — Anchors an opening phrase that leads naturally into hedged prose, and prefill is rejected on current models.

### BU4-010

**Q.** 11 explicit field-handling criteria but no rule for missing fields; outputs use `null`, `""`, and `"unknown"` inconsistently. Which change MOST directly stabilizes missing-field handling?

- A. Lower temperature so the choice becomes deterministic.
- B. Drop missing fields from the output entirely.
- C. Add the 12th criterion: "Missing fields must use `null`; never empty string, never sentinel strings."
- D. Use JSON mode so the output is always syntactically valid.

**✅ Answer: C**

**Why it's correct.** The inconsistency exists because **the case was never specified** — with 11 criteria covering present fields and none covering absent ones, the model improvises. Adding the twelfth criterion, with the alternatives explicitly forbidden, closes the gap. It also picks the semantically right marker: `null` means absent, whereas `""` and `"unknown"` are values that downstream code may treat as data.

**Why the others fail.**
- **A** — Determinism would fix one arbitrary marker, possibly `"unknown"`.
- **B** — Omitting keys makes "absent from the document" indistinguishable from "field not in this schema version", and breaks consumers expecting a fixed shape.
- **D** — All three current outputs are already valid JSON; syntax was never the problem.

### BU4-011

**Q.** "Apologize when the customer is upset" — some responses apologize for routine inquiries, others miss apologies after genuine complaints. Which change BEST calibrates the behavior?

- A. Lower temperature to make the apology choice deterministic.
- B. Always apologize first to be safe.
- C. Use few-shot with two upset and two non-upset tickets so the model learns the boundary.
- D. Specify trigger conditions for apology.

**✅ Answer: D**

**Why it's correct.** "Upset" is undefined, so the model is applying its own threshold — which is why it errs in both directions. Naming the triggers (explicit dissatisfaction, a service failure on our side, a repeat contact about an unresolved issue) gives a checkable condition instead of a mood judgement.

> **Discriminator against UD4-006 / UD4-015**, where few-shot beat explicit criteria: in those items the stem states that **detailed criteria were already tried and failed**, so the remaining move was demonstration. Here the current prompt is a single vague clause — explicit criteria have not been tried yet, and are the cheaper, more direct first step. Option **C** is the correct *escalation* if D proves insufficient.

**Why the others fail.**
- **B** — Apologising on routine inquiries is one of the two failure modes; making it universal entrenches it and reads as insincere.
- **A** — Determinism fixes the threshold in place rather than correcting it.

### BU4-012

**Q.** Two pipelines share a model with near-identical system prompts differing only in schema names (invoices vs. purchase orders). A developer suggests consolidating into one prompt with a runtime flag. MOST accurate assessment?

- A. Routing logic must always live in the system prompt for consolidation to work.
- B. Consolidation is always better because it reduces maintenance overhead.
- C. Two separate user messages on one consolidated prompt achieve the same isolation as two prompts.
- D. Consolidation increases prompt complexity and risks cross-document interference; keep specialized system prompts unless the deduplication win is large.

**✅ Answer: D**

**Why it's correct.** A consolidated prompt must describe **both** schemas, so every invoice extraction is performed with purchase-order fields in context — an invitation to field bleed, particularly where names are similar. It names the real trade-off and the right default: the duplication here is small (schema names), while the interference risk is on output correctness.

**Why the others fail.**
- **B** — "Always better" ignores the interference cost; maintenance savings on two near-identical prompts are minor.
- **C** — Sharing a system prompt means sharing the context; separate user messages do not isolate what the system prompt describes.
- **A** — Fabricates a rule; routing can live in application code, and it is not what makes consolidation succeed or fail.

**Source.** [System prompts](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/system-prompts) · [Prompt engineering overview](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/overview)

### BU4-013

**Q.** *(restatement of BU4-006 with the fix spelled out)* Refactors silently change function signatures. Which change MOST directly prevents this?

- A. Lower temperature to 0 so refactors become more conservative.
- B. Run the refactor through a linter after Claude finishes.
- C. Explicitly forbid signature changes — "Function name, parameter names, parameter order, and return type must remain identical."
- D. Use prefilling to start with `def` and the original function name.

**✅ Answer: C**

**Why it's correct.** The spelled-out version shows why it works: it enumerates **all four** components of a signature, so no part of it is left to interpretation. "Keep behavior the same" permitted a reading under which parameter renaming was harmless; this does not.

**Why the others fail.**
- **B** — A linter has no reference to the original signature.
- **A** — Temperature is not a conservatism control.
- **D** — Prefill is rejected on current models and would constrain only the first tokens.

**Source.** [Prompt engineering — be clear and direct](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/be-clear-and-direct)

### BU4-014

**Q.** Generated SQL migrations occasionally drop columns that should remain. Which prompt refinement BEST protects against unintended destructive schema changes?

- A. Explicitly state that existing tables and columns must not be dropped unless the prompt explicitly requests deletion.
- B. Lower temperature to make schema generation more deterministic.
- C. Ask Claude to generate shorter SQL scripts so accidental drops are less likely.
- D. Place the migration inside a Markdown code block so Claude treats it more carefully.

**✅ Answer: A**

**Why it's correct.** It states a **default-deny rule for the destructive operation** and names the single condition that lifts it. A model refactoring a schema may reasonably infer that a superseded column should go; this removes that inference and makes deletion something that must be asked for.

**Why the others fail.**
- **B** — Deterministic destructive migrations are still destructive.
- **C** — Length is unrelated to whether a `DROP COLUMN` is included.
- **D** — Formatting does not change the model's care; code blocks affect presentation.

> As with BU4-008, for production migrations the durable protection is a **review gate or a hook** that blocks destructive DDL — prompt rules reduce frequency but do not guarantee.

**Source.** [Prompt engineering — be clear and direct](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/be-clear-and-direct) · [Claude Code hooks](https://code.claude.com/docs/en/hooks)

### CS4-001

**Q.** A field the schema expects is simply not present in the source document. The extractor should:

- A. Fill the field with a plausible value inferred from the rest of the document.
- B. Return `null` for that field and mark it as not found, leaving the rest of the extraction intact.
- C. Fail the entire extraction because one field is missing.
- D. Repeat the previous record value for that field.

**✅ Answer: B**

**Why it's correct.** Absence is **information**, and it should be reported faithfully: `null` plus a not-found marker distinguishes "the document does not contain this" from "we did not look" or "the value is empty". Keeping the rest of the extraction preserves everything that *was* found, so one missing field does not discard a document's worth of correct data.

**Why the others fail.**
- **A** — Fabrication, and the most dangerous option: an inferred value is indistinguishable downstream from an extracted one.
- **D** — Cross-record contamination; strictly worse than A because it looks authoritative and correlates across records.
- **C** — Discards valid data over one absent field; missing fields are routine, not exceptional.

**Source.** [Structured outputs](https://docs.claude.com/en/docs/build-with-claude/structured-outputs) · [Prompt engineering — be clear and direct](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/be-clear-and-direct)

### CS4-002

**Q.** An invoice extractor reads dates like `03/04/2025` that could be March 4 or April 3. The design that avoids silent errors is to:

- A. Assume the United States month-first format everywhere.
- B. Require an ISO date in the output schema, and when the input is ambiguous, flag the field for review instead of guessing.
- C. Store the date as the raw string and sort it out later.
- D. Drop any date that is ambiguous.

**✅ Answer: B**

**Why it's correct.** Two mechanisms addressing the two halves. The **ISO schema requirement** makes the output unambiguous, so nothing downstream has to re-interpret it. **Flagging genuine ambiguity** rather than guessing is what makes the errors non-silent: a 50/50 guess is right half the time and wrong invisibly the other half, whereas a flagged field gets a human decision.

**Why the others fail.**
- **A** — Silently wrong on every non-US invoice, which is precisely the "silent error" the question asks to avoid.
- **C** — Defers the same ambiguity to a consumer with *less* context than the extractor had.
- **D** — Discards data that is usually resolvable from other document evidence, and loses the invoice's date entirely.

**Source.** [Structured outputs](https://docs.claude.com/en/docs/build-with-claude/structured-outputs) · [Building effective agents — escalation](https://www.anthropic.com/engineering/building-effective-agents)
